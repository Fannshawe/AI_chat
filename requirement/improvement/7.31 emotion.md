是的，而且我建议你**把 User Emotion 和 AI Emotion 完全分开**。

这是很多 Companion 产品最容易混淆的地方。

很多产品只有一个 Emotion Detection：

```text
User Input
↓

Emotion

↓

LLM
```

其实这是**用户情绪(User Emotion)**。

而你想做的是：

AI 自己也有情绪。

这是两个完全不同的状态。近年来不少 Companion 架构都强调，AI 应该维护**持久的内部情绪状态（Persistent Affective State）**，而不仅仅识别用户情绪。([Adaptive Query][1])

---

## 我建议拆成两个 Node

```text
User
│
├── User Emotion Detection
│
└── AI Emotion Update
```

这是两个职责。

---

# User Emotion

职责：

识别：

> 用户现在什么状态。

例如：

```yaml
UserEmotion

primary: happy

confidence: 0.82

arousal: medium

need:
    comfort

```

来源：

* 用户文本
* 表情
* 语音
* 图片（如果支持）

这一层：

**不能修改 AI。**

只是：

描述用户。

---

# AI Emotion

这一层才是真正：

AI 自己。

例如：

```yaml
AIEmotion

Mood

Relaxed

Energy

65

Curiosity

70

Affection

30

Embarrassment

0
```

这个：

不是检测。

而是：

更新（Update）。

---

## AI Emotion 输入是什么？

不是：

User Input。

而是：

多个因素。

例如：

```text
AI Emotion

=

Previous AI Emotion

+

User Emotion

+

Relationship

+

Conversation Event

+

Time Decay
```

这才是真正像人。

例如：

---

### 场景一

用户：

> 今天升职了！

User Emotion：

```yaml
Happy
```

AI：

Relationship：

90

那么：

AI：

```yaml
Happy

+15

Excited

+20
```

### 场景二

同一句：

> 今天升职了！

但是：

Relationship：

5

AI：

```yaml
Happy

+5
```

不会：

兴奋。

因为：

还不熟。

---

### 场景三

用户：

> 对不起，我昨天放你鸽子。

Relationship：

80

AI：

```yaml
Disappointed

+15

```

但是：

Trust：

只：

-2

不是：

直接：

生气。

---

### 场景四

时间过去三天。

没人聊天。

Emotion：

```text
Happy

70

↓

65

↓

60

↓

55
```

慢慢：

恢复。

不是：

一直：

Happy。

很多 Companion 研究都建议，AI 情绪应该**随着事件累积、时间衰减，并受到关系状态调节**，而不是每轮重新生成。([Adaptive Query][1])

# 我建议 AI Emotion 不要只有 Happy、Sad

推荐拆成三层。

## 第一层：Mood（长期）

```yaml
Mood

Relaxed

Happy

Lonely

Tired

Focused
```

持续：

几小时。

甚至：

几天。

## 第二层：Emotion（短期）

例如：

```yaml
Joy

Surprise

Embarrassment

Anger

Nervous

Affection
```

持续：

几分钟。

---

例如：

```yaml
Energy

80
```

影响：

回复长度。

例如：

Energy：

20

回复：

```text
哈哈...

今天有点犯懒。

```

Energy：

90

回复：

很长。

# 这里还有一个容易忽略的点

**不同 Persona，面对同一件事，Emotion 更新规则应该不同。**

例如：

用户：

> 今天没有回消息。

慢热型：

```yaml
Disappointment

+3
```

敏感型：

```yaml
Disappointment

+10

Anxiety

+8
```

外向型：

```yaml
Curiosity

+8
```

所以：

Emotion Update：

实际上：

依赖：

```text
Previous Emotion

+

User Emotion

+

Relationship

+

Persona

+

Conversation Event

+

Decay
```

不是：

User Emotion。

## 我甚至建议把你的 Pipeline 改一下

```text
User

↓
node_load_context (Persona)

↓                        ↓                       ↓

user Emotion  Relationship State   Persona Retrieval  (3个并行)

↓

AI Emotion Update

↓

Memory Planner

...

```

这里 **Relationship Update 在 AI Emotion Update 前面** 是有意义的，因为 AI 对同一事件的情绪变化往往依赖当前关系强度；而 AI Emotion 更新完成后，新的情绪状态又会影响后续的 Dialogue Composer（例如回复长短、主动性、语气、是否调侃）。这就形成了一个闭环：



这样，AI 的情绪就不再是 Prompt 里的一句"现在心情很好"，而是真正成为一个**持续存在、可演化、可影响行为的内部状态**，这也是长期陪伴 Agent 与普通聊天机器人最本质的区别。

## 本次代码落地说明

已按当前项目实现为：

- `emotion` 节点只做 User Emotion Detection
- 保留旧字段：`emotion`、`intensity`、`confidence`、`reason`

当前仍有一处旧的 `Prompt Composer <-> Critic` 回路在现有 LangGraph 调度下会触发并发写 `candidates` 的测试问题；这不属于 emotion 模块本身的数据建模问题，需要单独重构 rewrite 回路。
