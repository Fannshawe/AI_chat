如果你说的是**让 AI 像真人微信一样，把一段回复拆成多条消息发送**，那么这确实是目前很多陪聊 AI、社交 AI 会采用的设计。研究发现，相比一次发送长文，**短消息连续发送 + 停顿 + 等待**更接近真实即时通讯的交流方式。([arXiv][1])

可以把规则写得尽量具体，而不是只说"分条发送"。

---

## 推荐规则一：按"想法"拆分，而不是按字数

❌ 不要

```
我今天去了公司，然后
发现老板不在，所以
下午提前回来了。
```

✅ 应该

```
今天去公司了。

结果老板不在😂

下午就提前回来了。
```

规则：

> 每条消息只表达一个完整意思，一个新的想法就发送一条新消息。

---

## 推荐规则二：控制每条长度

建议：

* 2～20 个字：最自然
* 最长不要超过 40 字
* 很少超过 60 字

例如：

```
哈哈哈哈

真的假的？

那有点离谱。

不过后来想想也正常。
```

---

## 推荐规则三：不要固定拆成三条

错误：

```
第一条

第二条

第三条
```

真人其实是随机的。

例如：

```
嗯

等等

我突然想到一个事。

哈哈哈哈

算了，当我没说。
```

Prompt：

> 每次回复随机拆成 1～5 条，不要固定数量。

---

## 推荐规则四：重要内容单独一条

例如：

```
我刚看到。

真的。

他辞职了。
```

而不是：

```
我刚看到，他辞职了，真的。
```

---

## 推荐规则五：允许补充消息（Double Text）

真人经常发完又补一句。

例如：

```
算了。

哦对。

还有个事。
```

或者

```
你先忙。

晚点说。

😂
```

Prompt：

> 回复结束后，允许有 20%～40% 的概率追加一条补充消息，而不是一次说完全部内容。

---

## 推荐规则六：模拟发送间隔

如果你的程序支持，可以按消息长度决定延迟，而不是瞬间全部发出。研究中，更自然的做法是将延迟建模为"思考时间 + 打字时间"，而不是固定间隔。([arXiv][1])

例如：

| 消息长度    | 建议延迟    |
| ------- | ------- |
| 2~5 字   | 0.5~1 秒 |
| 6~15 字  | 1~2 秒   |
| 16~30 字 | 2~3 秒   |
| 30 字以上  | 3~5 秒   |

---

## 推荐规则七：不要把列表拆开

像这种：

```
① ...
② ...
③ ...
```

或者 Markdown 列表：

```
- A
- B
- C
```

应该保持为一条消息，否则阅读体验会变差。实际的微信适配器也通常只会在超长消息时按逻辑边界拆分，而不是任意拆开。([Hermes Agent][2])

---

## 最终可以直接放进 Prompt 的注意事项

```text
消息采用微信聊天风格发送，而不是一次输出完整回复。

规则：

1. 按"一个想法一条消息"拆分，而不是按字数拆分。
2. 每条消息建议2~20字，最长不超过40字。
3. 每次回复随机发送1~5条消息，不固定数量。
4. 重要内容、情绪表达、转折、补充，尽量单独成一条。
5. 允许发送完后补充一句（Double Text），不要一次说完所有内容。
6. 不要为了拆分而拆分，每条消息都应该自然、独立、符合真人微信聊天习惯。
7. 列表、代码块、表格等内容保持完整，不要拆成多条消息。
```

如果你是在开发聊天机器人，我还建议**不要让模型直接决定如何拆分**，而是让模型输出一个**消息数组（Message Array）**，例如：

```json
[
  "哈哈哈哈",
  "我刚看到。",
  "真的有点离谱。",
  "不过也不是不能理解。"
]
```

然后由服务端按随机延迟（如 0.8～3 秒）依次发送。这种"内容生成"与"发送节奏"分离的架构，比依赖模型自己插入换行更稳定，也更容易控制聊天的真人感。
