## 解释说明

1. 最终定下这样设计，关键动态统一归入 Memory 并由用户手动更新

2. Long Memory

不要只保存聊天记录。

建议拆成四种Memory。

Memory Retrieval
│  （分类读取和存储）
├── Episodic Memory （经历，带时间）
├── Semantic Memory  （事实）
├── Emotional Memory  
└── Shared Experience

  1. Episodic Memory（事件）（带时间）

  ```
  2026-05-01

  今天和用户聊了创业。

  用户推荐我看《三体》。

  感觉挺有意思。
  ```

  ---

  2. Semantic Memory（事实）

  ```
  用户叫Fan

  用户喜欢AI

  用户在创业
  ```

  ---

  3. Emotional Memory

  ```
  用户夸过我。

  用户最近比较焦虑。

  用户最近创业压力很大。

  我希望以后多鼓励他。
  ```

  ---

  4. Shared Experience

  ```
  两人共有的经历

  ```

  这样以后Prompt就会不同。

  ---

3. Memory Planner：根据对话决定"检索什么"，而不是全部检索。
4. Reflection：决定"记住什么"，而不是把所有内容都存下来。
5. 内容整合其实应该叫 Prompt Composer，它根据之前node的信息和建议，最后来生成最终的回复。
6. 关系行为边界从LLM处获取，不是指导文档。
7. Reply Critic 如果失败，需要给出修改建议到 Prompt Composer


## 下面我会规范每个模块

### 已确认的实现决策

- Persona 只保留 Core、Personality、Habit。Dynamic Growth 删除，其有效变化由 Reflection 更新 Habit。
- Core 与 Personality 每轮固定注入；Persona Retrieval 只检索相关 Habit。
- Core 变更由 Reflection 生成提案，人工确认后写入；Personality 只能人工编辑；Habit 自动更新。
- User Emotion 与 AI Emotion 分离。User Emotion 只描述用户当前情绪；AI Emotion 负责更新 AI 的持久内部状态。
- Relationship 使用 Trust、Familiarity、Intimacy、Attraction、Attachment、Comfort 六维 0-100 分值。
- Relationship Stage 为：陌生人、熟人、朋友、亲密朋友、暧昧、恋人。由 LLM 判断；只有严重事件允许降级。
- Relationship 不保存 Shared Experience；Shared Experience 只属于 Memory。
- Reply Critic 最多触发两次重写，仍失败时返回综合评分最高的候选并记录告警。
- 所有记录只保存真实发生时间，例如 `created_at`、`updated_at`、`state_date` 这类时间属性；不要把 `hours_ago/days_ago` 这类时间差写回记录本身。
- 所有关键时间信息必须显式传入 LLM，包括：`now`、每条记录自带的真实时间戳、上次 AI Emotion 更新时间、事件时间、记忆时间范围。若某节点需要时间差，应在节点运行时基于这些真实时间计算，禁止让 LLM 自己猜“过了多久”。

### 关于并发问题

- 这里的“并发问题”不是 Python 线程问题，而是 LangGraph 的状态合并规则。
- 如果同一个 step 里有两个节点同时写同一个普通字段，例如 `candidates`，LangGraph 会报冲突。
- 当前最容易出问题的是 `Prompt Composer -> Critic -> Prompt Composer` 的回路；如果回写和前向写落在同一调度 step，就会同时更新 `candidates`。
- 因此图结构需要保证：同一 step 中，同一字段只有一个写入者；或者该字段必须设计成可聚合通道。

## Node 规范

### 1. Context Loader

- **Responsibility**：按用户加载短期历史、Persona Core/Personality/Habit、关系状态和近期情绪。
- **Input**：`contact_id`、`user_request`、图片和模型配置。
- **Output**：固定上下文及三条并行分支所需 State。
- **Mutation**：是，只修改本轮 State。
- **Persistence**：否。

### 2. User Emotion

- **Responsibility**：识别用户当前情绪，保留旧字段输出，不更新 AI 自身状态。
- **Input**：最新消息、近期对话、近期情绪记录（记录内只含真实时间戳）、显式时间信息。
- **Output**：`EmotionAnalysis`。
- **Mutation**：是，写入 `emotion_analysis`。
- **Persistence**：延迟到 Content Save。

### 3. Relationship State

- **Responsibility**：判断六维分值变化、Relationship Stage、严重事件及本轮行为边界。
- **Input**：当前关系全量状态、最新消息、近期对话（记录内只含真实时间戳）、显式时间信息。
- **Output**：`changes`、`suggested_level`、`stage_reason`、`serious_event`、`behavior_boundaries`。
- **Mutation**：是，写入 `relationship_analysis`。
- **Persistence**：延迟到 Content Save；单维单轮变化限制在 `[-10, 10]`，记录前后值和原因。

### 4. Persona Retrieval

- **Responsibility**：只从 Habit 中选择与当前话题相关的条目。
- **Input**：完整 Habit、最新消息。
- **Output**：`relevant_habits`。
- **Mutation**：是，只修改本轮 State。
- **Persistence**：否。

### 5. AI Emotion Update

- **Responsibility**：根据 Previous AI Emotion、User Emotion、Relationship、Persona emotionProfile、Conversation Event 与显式时间信息，更新 AI 的持久情绪状态；若需要衰减值，由本节点基于真实时间自行计算。
- **Input**：`previous_ai_emotion`、`user_emotion`、`relationship`、`persona_emotion_profile`、`recent_events`、`time_context`；其中各记录只携带真实时间属性。
- **Output**：`events`、`ai_emotion`。
- **Mutation**：是，写入 `ai_emotion_analysis`。
- **Persistence**：延迟到 Content Save。

以上 User Emotion、Relationship、Persona Retrieval 可并行，但进入后续节点前必须完成统一汇合；AI Emotion Update 读取这些结果后再继续向下游流动。

### 6. Memory Planner

- **Responsibility**：决定检索什么，并对话题进行近义词和关联关键词扩展；不直接读取 Memory。
- **Input**：最新消息、近期对话、用户情绪、AI Emotion、关系分析、可用 Memory 类型、显式时间信息；时间差由本节点按需计算。
- **Output**：每项包含 `memory_type`、`query`、`keywords`、`priority`、`top_k`、`time_range`、`reason`。
- **Mutation**：是，写入 `memory_plan`。
- **Persistence**：否；`reason` 随 generation 快照保存用于调试。

### 7. Memory Retrieval

- **Responsibility**：按 Planner 请求分类检索并去重排序。
- **Input**：Memory Plan、`contact_id`。
- **Output**：Episodic、Semantic、Emotional、Shared Experience 中命中的记忆。
- **Mutation**：是，写入 `memories`。
- **Persistence**：否。

### 8. Chat Skill Retrieval

- **Responsibility**：从现有 Markdown 文档检索交流技巧，不决定关系行为许可。
- **Input**：最新消息、阶段、情绪。
- **Output**：相关文档片段。
- **Mutation**：是，写入 `guidance_chunks`。
- **Persistence**：否。

### 9. Dialogue Composer

- **Responsibility**：只形成 Plan 和建议，不写最终回复。
- **Input**：对话、Persona、相关 Habit、User Emotion、AI Emotion、Relationship、Memory、聊天技巧文档、显式时间信息；各记录只包含真实时间戳。
- **Output**：Goal、Strategy、Structure、Memory Usage、Persona Expression、Emotion Expression、Topic Plan、Constraints。
- **Mutation**：是，写入 `dialogue_composition`。
- **Persistence**：随 generation 快照保存。

### 10. Prompt Composer

- **Responsibility**：整合全部上游状态，生成三个最终候选；接收 Critic 修改建议重写。
- **Input**：最新消息、历史、固定 Persona、相关 Habit、User Emotion、AI Emotion、Relationship 边界、Memory、Dialogue Plan、`rewrite_instruction`、显式时间信息；时间差由当前节点按需派生。
- **Output**：三个候选回复。
- **Mutation**：是，写入 `candidates`。
- **Persistence**：候选随 generation 快照保存，不自动写入真实聊天历史。

### 11. Reply Critic

- **Responsibility**：检查 Style、Persona 和 Memory 一致性，并检测 AI 味、采访味和过度共情。
- **Input**：候选、Persona、相关 Memory、Dialogue Plan、近期对话。
- **Output**：逐候选评分、`passed`、问题和 `rewrite_instruction`。
- **Mutation**：是，累计评审次数与最佳候选；失败时路由回 Prompt Composer。
- **Persistence**：随 generation 快照保存。

### 12. Reflection

- **Responsibility**：决定哪些内容值得长期保存，以及是否更新 Habit 或提出 Core 修改。
- **Input**：最新真实消息、历史、相关旧记忆、当前 Habit、生成候选、显式时间信息；记录本身只保存真实发生时间。
- **Output**：分类 Memory、`habit_updates`、`core_update_proposals`。
- **Mutation**：是，写入 `reflection_analysis`。
- **Persistence**：延迟到 Content Save。Personality 禁止自动修改。

### 13. Content Save

- **Responsibility**：统一提交用户情绪、AI Emotion、关系变化、Conversation Event、Reflection Memory、Habit 更新、Core 提案和 generation 快照。
- **Input**：完整 Workflow State。
- **Output**：`generation_id`、最新 Relationship 和输入消息 ID。
- **Mutation**：是。
- **Persistence**：是，所有自动写入集中在此节点。
